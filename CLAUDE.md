# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
docker compose up --build          # the panel on http://localhost:8080 with PostgreSQL
docker compose up -d db            # PostgreSQL alone, on localhost:5432, for local runs and integration tests
make css build                     # Tailwind CSS into web/static/css/app.css (not committed), then bin/weather-panel
DATABASE_URL='postgres://weather:weather@localhost:5432/weather?sslmode=disable' make run
make test                          # go test ./...; PostgreSQL integration tests skip without TEST_DATABASE_URL
TEST_DATABASE_URL='postgres://weather:weather@localhost:5432/weather?sslmode=disable' make test
go test ./internal/weather -run TestParseQuery   # a single test
make generate                      # templ and sqlc; commit the generated code
make check-generated               # CI: fails when the committed generated code is stale
make test-browser                  # chromedp tests (build tag browser) against the running panel; needs Chrome
make perf                          # AC-09 measurement against the real Open-Meteo (tags browser,perf)
```

CI (`.github/workflows/ci.yml`) runs `make check-generated`, `go vet -tags browser,perf ./...`, and
`go test -race ./...` with a PostgreSQL service. Browser and performance tests run only locally, against the panel
from `docker compose`.

## How the documents relate

- `docs/prd.md` states what and why and is deliberately technology-agnostic: no languages, frameworks, databases, or
  frontend/backend wording. Stack and architecture belong in `docs/techspec.md`. The only technology the PRD names is
  Open-Meteo, because its license, attribution, and rate limits shape the product.
- `docs/techspec.md` states how and cites PRD IDs (`US1`–`US6`, `FR1`–`FR14`, `AC-01`–`AC-13`). Adding, removing, or
  renumbering a requirement means updating the references in both files, including ranges such as `FR5–FR8`.
- Documentation and commit messages are in English. The product UI is Brazilian Portuguese: every label, message, and
  weather-condition description shown to users.
- Commits follow Conventional Commits (see `git log`).

## Architecture

- One Go service with the chi router renders every page state server-side with templ. The search is a plain `GET` form
  to `/weather`; htmx swaps the response into the `#result` region. The handler returns a fragment when the request has
  `HX-Request: true` and the full page otherwise (no-JavaScript fallback), with `Vary: HX-Request`.
- The outcome sets the status code: `200` success, `422` invalid input, `404` city not found, `502` upstream error,
  `504` upstream timeout. The design depends on htmx 4 swapping error responses into the target.
- Lookup flow: normalize the input (trim, collapse whitespace, NFC, at least two letters or digits, at most 100 runes),
  then geocoding cache → Open-Meteo Geocoding API (`count=1`, `language=pt`), then weather cache keyed by the Open-Meteo
  location id → Forecast API with explicit units. The whole lookup runs under one 2.5 s deadline with no retries.
- PostgreSQL is only a best-effort cache (found location 30 days, not found 1 day, conditions 10 minutes). A database
  error at runtime must not fail a lookup; a migration failure at startup must stop the service.
- FR14 (the browser never sends a lookup to a third party) is enforced by the CSP `connect-src 'self'` and by serving a
  vendored htmx from the same origin. Do not add CDN scripts, inline scripts, or `hx-on` handlers; the CSP blocks them.
- Screen readers hear each outcome through `#announcer`, a hidden status region that every htmx response fills out of
  band (`hx-swap-oob="innerHTML:#announcer"`) with one text in reading order. `#result` is deliberately not a live
  region: a screen reader pass showed a live region receiving a whole result reads it piece by piece and out of order.
- Static files are served with a one-year immutable cache. Pages reference them through `web.AssetPath`, which adds a
  content version; files referenced by fixed URLs, such as the vendored fonts, carry their version in the file name.
- Logs never contain the city, the resolved location, the query string, or client IP addresses.
- Code generated by sqlc (`internal/store`) and templ (`*_templ.go`) is committed; the generators are pinned as `tool`
  directives in `go.mod`.

## htmx 4, not htmx 2

The project targets htmx 4.0 (released 2026-08-28). Most examples online, and most model knowledge, describe htmx 2,
whose attributes and defaults differ:

- `hx-disable` disables elements during a request (it was `hx-disabled-elt`); `hx-ignore` skips htmx processing (it was
  `hx-disable`).
- Inheritance is explicit through the `:inherited` suffix; `hx-inherit` and `hx-disinherit` are gone.
- `4xx` and `5xx` responses are swapped like any other; `hx-status:<code>` overrides the behavior per status.
- Events follow `htmx:phase:action`, for example `htmx:before:request` and `htmx:after:swap`.

Check attribute behavior in the htmx 4 docs (htmx.org, or `www/src/content/` at tag `v4.0.0` of
`bigskysoftware/htmx`), not from memory.
